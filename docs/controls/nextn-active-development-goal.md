# NextN 当前总 Goal 与工作约束

## 活跃 Goal 提示词

持续把 NextN 交付为可长期使用、功能正确、状态可靠、视觉和交互一致的 HarmonyOS
应用。NextE / ErosN 是实现语义与页面结构的参考：每次改动先完整映射同一页面的
scroll owner、固定 chrome、容器层级、section 顺序、子项几何、加载/错误/空状态及
动作所有权，再复用已有 scaffold、组件和状态模式。NextN 的数据源、账户模型、NH
能力和已存在产品差异必须保留；仅替换有证据的数据叶或不支持叶。代理主动审查当前
父树中同层级的明显缺陷，但用户指出一个问题时，只改其被证明的边界，绝不借机扩大
为未经授权的行为替代、功能删除或整页重写。

账户持久化是条件抢占 P0：任何**当前**原生 Account 或 Favorites 证据一旦证明会话
缺失或不可用，立即冻结其它工作，把“找出并消除登录失效”作为唯一问题。先记录
无敏感 S0、开始计时并采集恢复/401 阶段；从唯一状态所有者开始追踪所有读取、写入、
删除、失效、迁移、请求重试与进程死亡顺序，且只修复被当前证据证明的错误状态转移。
重新登录是修复后的 record-present 验证，不是掩盖原因的替代品；登录使用固化的连续
语义 WebView 流程，一次账户输入、一次密码输入、一次提交，除 CF/挑战分支外不中断
思考或改走别的路径。每个失效/登录周期写入
`docs/qa/nextn-login-attempt-ledger.md`，记录检测时间、WebView 可见时间、成功/最后
观察时间、耗时、首个阻塞阶段、次数和累计耗时，但绝不记录凭据、cookie、URL、个人
资料、原始布局或截图。P0 只有在真实登录经 force-stop/cold start 后原生 Account
保持认证、Favorites 完成 authenticated read，并在仓库写出已验证根因、此前多轮失败
原因、错误假设、缺失证据和防复发约束后才解除。

所有 UI 和设备操作严格分为“建链”与“执行”。首次通过当前状态、参考和必要截图建立
语义入口、通用 direct intent 或会改变下一步的真实分支；链路一旦确认，普通动作必须
连续执行到底，禁止在每个点击之间重新读源码、截图、dump 布局、推理、发状态或猜旧
坐标。重复页面优先使用已经证明的通用 direct intent 或语义入口，例如
`galleryId + destination=comments`。截图/多模态仅用于首次建链、真实决策门、最终验收
或异常诊断；终态不符时保存一份命名审计证据，修复整条链后再执行。用户要求审计时，
截图保存在命名本地目录，不自动删除，也不提交原图。

横向滚动设计遵守一个精确边界：只有可滚动的 List 视口可以穿透副容器的**横向内部
inset**，使中段滚动具有连续延展感；List 的第一项与最后一项各自承担 leading/trailing
留白。标题、分组头、正文、圆角卡片、垂直间距和上下边距仍属于父容器，不得因这条
规则被移出、裁掉或清零。它不是“所有四边无边距”，也不是把 header 扩到卡片外。Preview、
Related、横向评论及任何同型 rail 均按这条职责拆分；尺寸、标题可读性、封面与文字
比例必须先以同状态真实画面和完整参考树判断，禁止凭感觉极端压缩或放大。

浮动操作的定义是固定在视口上层、允许滚动内容从其下方经过；中途遮挡不是缺陷，也
不得据此增加列表边距、隐藏、下沉或改位按钮。唯一需要检查的是终端内容能否滚到该
操作上方并保持可达。任何改变这项浮动所有权的提议，必须先有明确用户指令和对应
参考父树证据。

禁止创建、运行、更新或引用 UI 静态合同、source-shape 检查、合成 fixture、布局
matcher 或自造摘要工具作为视觉/交互验收。构建、安装、源码相似和孤立单帧都不是
视觉完成；所有可见结论必须来自同状态、同视口真实设备与参考对照。每项功能或布局
改动完成后，立即核对精确 diff、运行 `git diff --check`，并提交一个只包含该项的独立
commit；不积累未提交的 UI/功能修改，不把不相关工作混入一个提交。发现新的独立问题，
以新的窄改动和新提交处理。

**UI 变更理由硬门：**任何可见 UI 改动（包括尺寸、间距、字体、标题、容器、滚动、
浮层、加载态和回退）在改代码前，必须先在
`docs/qa/nextn-ui-change-ledger.md` 写一条记录：用户指令或真实参考/设备证据、完整父树
边界、精确前后值或结构、为何只改该边界、验证计划与未解决风险。不得以“优化”、
“紧凑”、“平衡”、“看起来更好”等主观词作为理由。每个包含 UI 代码的提交必须同时
包含对应 ledger 条目；事后发现为错误的改动，必须补充其错误假设、忽略证据、影响和
明确防复发约束，才可进行下一次同区域 UI 修改。ledger 不是 UI 静态合同，不能替代
真实同状态视觉对照，也不能宣告验收通过。

任务不会因为质疑、构建、局部截图、源码审查、子任务结束或暂时无同状态参考而停止。
每次恢复都先确认当前活跃目标、未证明边界和下一项实际动作；只有用户明确停止，或
所有声明结果均已有要求的真实证据，才允许结束。

**终止与阻断硬门：**一次提交、构建、截图、局部审查或“本轮暂时没有改码”只可作为
检查点，绝不能触发 final、任务结束或 Goal 阻断。每次准备结束前必须明确检查：当前
Goal 是否已获得规定的完整证据；若否，必须继续已记录的下一项动作。只有用户明确停止
或已通过非沙箱、同一选定目标的真实操作证明存在外部阻断时，才可报告阻断。尤其是
沙箱内 HDC 的 `Connect server failed` 只说明该沙箱不能连接本机 HDC server：必须先在
同一选定设备上用非沙箱 HDC 复核 `tconn/list targets/echo`，不得据它写设备离线、停止
会话或标记 Goal blocked。Goal blocked 还要求三个连续恢复回合均有这种非沙箱复核的相同
外部失败，并确认不存在别的已授权、同范围下一步。

## 当前执行顺序

1. **P0（条件触发）账户持久化**：按上文抢占；没有新鲜失效证据时不得用旧观察阻断
   其它工作，也不得把历史登录结果冒充当前证据。
2. **P1 全局页面复核与窄修复**：Detail 当前冻结为已记录基线（Preview `150vp`、横向评论
   预览 `120vp`、Read 保持浮动），没有新的明确用户反馈和同状态证据不得重新打开。
   接下来沿真实主路径逐页审查根列表、Search、Reader、Downloads、Settings 和未完成能力；
   每次只选择一个被当前视觉或参考证实的父树问题，完成理由台账、窄改动、独立提交和
   同状态实机复核后才进入下一页。不得用“全页面待办清单”替代逐项交付，也不得把一个
   页面的局部反馈扩展为其它页面的重构。
3. **P2 深层能力与边界状态**：在 P1 的当前页面问题逐项收束后，沿真实主路径审查
   Favorites、History、Downloads、Reader、Settings 等页面族的功能和生命周期；不删除
   NH 能力，也不用参考缺失替代现有产品行为。

## 不能替代本 Goal 的文件

`AGENTS.md`、`docs/controls/nextn-execution-integrity.md` 和登录设备协议中的更严格规则
优先；它们与本 Goal 一起约束每个恢复的回合。
