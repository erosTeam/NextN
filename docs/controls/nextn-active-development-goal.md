# NextN 当前开发总目标与执行规范

## 当前 Goal 提示词

持续完成 NextN 的产品开发与真实验收：以 NextE / ErosN 的完整父树、交互所有权和
状态流为默认参考，保留 NextN 的数据源与产品差异；先修复已发现及同层级的设计、
生命周期与功能缺口，再推进未完成页面与功能。任何当前或新发现的登录状态丢失，
立即冻结其他开发并提升为唯一 P0：先从当前设备和完整的持久化状态机定位、修复并
验证根因，禁止把重新登录当作解决方案。仅在修复后的构建需要一个真实 record-present
会话来验证时，才使用既定的无清数据、语义 WebView 登录流程；它是验证工具，不是
恢复开发的门槛，更不能掩盖失败。P0 只有在真实登录后冷启动原生账户保持、
authenticated Favorites 成功且复盘写明根因后才能解除。不得把源码阅读、构建、静态
检查、单帧截图或重新登录本身描述为完成；每一项可见改动必须以同状态、同视口的
真实设备与参考对照验收。任务在用户显式停止或所有已声明结果得到真实证据前保持
active。

## 优先级

1. **P0 — 账户状态可靠性**
   - 一旦当前 S0 观察到原生账户或 Favorites 失去已认证状态，立刻暂停 UI/功能开发。
   - 先记录无敏感 S0、恢复/401 阶段和计时；随后只做根因工作：标出唯一状态所有者，
     枚举所有写入、删除、失效、迁移、请求重试和进程死亡顺序，找出可被当前证据
     证伪的具体错误转移；修复后构建并部署。重新登录前不得跳过这一根因边界。
   - 只有修复后的验证确实需要新 record-present 会话时，才走
     `docs/device-protocols/nextn-account-login-acceptance.md` 的固化路径。路径只包含：
     当前页面 → 直达可见登录 WebView → 语义账号输入一次 → 语义密码输入一次 →
     唯一一次 CF 可见判断 → 唯一语义提交 → 原生提升。不得在这段流程中插入分析、
     构建、文档、重新路由、重新输入或第二次提交。
   - 登录后必须 force-stop/cold-start（不清数据）并验证原生账户和 authenticated
     Favorites；任一失败都回到根因修复，绝不以再次登录代替修复。
   - 每次失效/登录周期写入红色账本：发现时间、WebView 可见时间、原生结果或最后
     观察时间、耗时、首个阻塞阶段、次数与累计耗时；绝不记录凭据、cookie、URL、
     个人资料、原始布局或截图。

2. **P1 — 参考驱动的页面与交互修复**
   - UI 不是“功能相近”即可：先映射同一页面的完整父树，包括 scroll owner、固定
     chrome、section 层级、子项顺序、几何、状态转移与动作所有者。
   - 优先复用 NextE / ErosN 已有框架、scaffold、组件和状态模式；NextN 差异只能替换
     数据叶、动作叶或确有证据的未支持叶，不能借机重写父树或改变已有产品能力。
   - 横向可滚动列表：页面级安全 gutter 可以保留，副容器/卡片的外边界、圆角、背景、
     标题位置和整体留白也必须保持。List 的 viewport 应覆盖卡片**内部完整宽度**，不能
     再被卡片的第二层左右 content inset 缩窄；但首项前与末项后的原有视觉留白必须
     保留，并且只能由 List 自身的 leading/trailing content padding 或 spacer 承担。
     因而中段滚动时内容可以进入原先的卡片内边距区域，形成延展感；它仍不得越过卡片
     外边界，标题和其他非滚动节点更不得越出卡片。修改前后必须并看初始、中段、末尾
     和卡片头部四个状态。缩略图预览、Related、Reader 缩略图以及所有同类横轨都按此
     规则审查；只在参考明确要求不同 clip/inset 时例外。
   - 普通切页、返回保留页或重新显示不应自动触发页一刷新、清空行或闪烁 loading。
     首次加载、用户下拉、根 tab 重点、真实数据 revision、查询变更和分页必须由明确
     的状态所有者区分。

3. **P2 — 未完成页面与功能**
   - 先对当前页面做完整源与真实 UI 审查，再决定下一条最有影响且证据充分的缺口。
   - 任何新功能必须保留现有 NH API/数据能力，不得把“参考中不存在”误改为删除、
     搜索替代或行为降级。

## 不可违反的验证与工作方式

- **禁止以 UI 静态合同、source-shape 检查、合成 fixture、布局 matcher 或自造
  摘要工具作为视觉/交互验收。**它们不能新建、运行、更新或被引用为 UI 已通过的
  证据。
- 源码/构建/安装只能说明各自事实；可见或持久化结论必须来自真实设备的对应状态。
- 可见修改前必须做同页 sibling review；发现一个布局缺陷时，审查同一父树内的相关
  section，不能只钉住用户指出的一个像素点。
- 所有可见验收使用同状态、同视口的 NextN 与参考实机/实图；无法建立可比状态时，
  明确写“未验收”，不以相似源码替代。
- 每次实现只解决一个被证据支撑的边界；不把修 A 扩展成未经授权的 B，也不增加新
  的本地状态、魔法间距、替代行为或平行架构。
- 每个更改完成前检查精确改动范围、构建与相关真实路径；若工作区不是 Git worktree，
  如实记录，不能伪造提交/差异证据。
- 用户的纠正、质疑或状态问题只改变相关细节，不结束活跃目标；除非用户明确停止，
  继续下一个已记录的安全行动。

## 当前恢复队列

1. 审查并修复详情页所有二级横向轨道的父容器 inset/clip 行为，先从缩略图预览和
   Related 开始；真实同视口对照后才接受。
2. 对已报告的详情页布局、全缩略图入口、Read rail/页面尾部、Related 与 Comments
   的完整父树和状态行为进行一次整体复核；不以局部补丁替代。
3. 继续按页面族审查剩余未完成功能与重复加载/刷新行为，优先处理有真实设备证据且
   影响用户主路径的缺口。
4. 若 P0 再次触发，立即冻结 1–3，先完成根因修复与真实持久化证明；仅将固化登录
   流程用于修复后的 record-present 验证，成功后从被冻结的具体条目继续。

本文件是当前开发的唯一总控说明；`AGENTS.md`、
`docs/controls/nextn-execution-integrity.md` 和设备登录协议中的更严格约束始终优先。
