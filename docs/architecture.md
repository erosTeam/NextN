# NextN architecture

## Reference boundary

- **NextE** supplies the HarmonyOS-native architecture: `entry` is the shell and cross-feature coordinator; `shared` has no feature dependency; feature HARs depend only on `shared`. ArkTS UI uses State Management V2 only.
- **ErosN** supplies the behavior contract for NH: read-only v2 browse, search, detail and reader data mapping. Its Flutter/OHOS embedding, signing assets, and WebView workaround are intentionally not migrated.

## Implemented slice

```text
entry shell
  -> home (latest v2 browse, session-local language/order controls, and a popular destination)
  -> search (v2 query, local recent searches, and local dictionary suggestions)
  -> gallery (detail v2, best-effort related galleries, public read-only comments, optional local tag labels)
  -> reader (native vertical or page-at-a-time image sequence, private page-byte cache, and verified app-private download source)
  -> user (local reading history, resume, and visible browser account session)
  -> download (durable user-initiated private gallery queue and direct local Reader entry)
  -> settings (scope and capability status)
shared
  -> semantic theme tokens, page states, gallery domain DTOs, HTTP client, local RDB repositories
  -> optional tag dictionary download, strict parser, exact namespace/raw-name lookup, and bounded local prefix suggestions
```

`entry` owns all route transitions. The feature modules expose only `Index.ets` barrels; they do not import each other.

## Navigation semantics

- `entry` owns one `HdsNavigation` / `NavPathStack` pair. Browse, Favorites, History, Downloads, and Settings are the retained root destinations inside one `HdsTabs` shell.
- Search, Popular, Gallery, Comments, Reader, Account session, and the Settings subpages are pushed destinations. System Back therefore restores the originating list or History context instead of collapsing to the launcher.
- Route payloads live in `entry`; feature HARs receive only parameters and intent callbacks. This retains the NextE dependency direction while keeping NextN's three verified roots compact.

## UI rules

1. Use system semantic colors first and keep NextN-specific aliases in `ThemeTokens`.
2. Use tokenized spacing, radii and type sizes rather than page-local visual literals.
3. Model loading, error and empty states independently so a refresh failure does not erase usable content.
4. Use `@ComponentV2`, `@Local`, `@Param`, `@Event` and `@ObservedV2` only. Do not introduce V1 decorators.
5. First-page refresh preserves usable rows. Pagination appends only after the list approaches its tail (or after an explicit footer action); it must deduplicate results and discard stale requests.
6. Reader and Gallery visual state must not revoke a verified detail merely because the reader is pushed. Returning to Gallery keeps the current Read action usable.
7. A reader-image failure is local to that page. Its retry replaces only that page's private cache entry and starts one new user-triggered GET; it never reloads reader metadata, resets list position, or overwrites stored reading progress.
8. Reader cache M0 stores only pages that enter the rendered Reader range in the app-private `cacheDir`. A stream writes `*.part` and atomically promotes a non-empty file on success; a bounded LRU removes old files. Settings may expose only aggregate private-file count/size and a user-confirmed clear action. Clear waits for existing streams to settle, skips a route-transition race, and never touches history, tag data, public storage, or remote state. It is not a download queue, public-storage export, background task, or whole-gallery offline claim.
9. Remote covers are presentation-only. A thumbnail or hero-cover failure must fall back to a neutral local placeholder and must not block list navigation, Gallery metadata, or the Read action.
10. A Gallery tag is a navigable anonymous-search affordance only when its ErosN-derived query syntax is known. The entry shell owns the typed search route; Search consumes the initial query once so Back preserves the original Gallery and Read state.
11. Recent searches and reading-history records are strictly local RDB data. Submitted search terms are recorded before the GET, deduplicated case-insensitively, retained to 50 entries, and may be reused or removed without changing remote state. Reading History may filter its loaded local snapshot by title or id and group matching rows by local calendar day; neither action queries a service or changes stored records. A reading-history entry may be removed only after its explicit long-press confirmation, and the entire local table may be cleared only after an explicit HDS title action and confirmation; neither action touches remote state, sessions, or the Reader cache. History mutations are serialized, so a Reader write already in flight cannot recreate a row after a later local remove or clear.
12. Public comments are a separate Gallery destination. They are anonymous GET-only data and may render only author name, date, and text; the card list, empty state, and local retry never delay or invalidate Gallery detail or Read.
13. The comments parser accepts only a top-level array or an explicit `result`/`comments` array envelope. Error objects are never treated as a successful empty discussion.
14. Tag translation is an optional local display layer. It is updated only after an explicit Settings action, downloads a fixed public asset through HTTPS without cookies or credentials, validates/decompresses it in private temporary storage, and atomically replaces the local dictionary only after parsing succeeds. Lookup uses the exact normalized `(namespace, raw_name)` pair; it never changes the raw tag query.
15. Account session M1 is an isolated, visible, user-triggered regular ArkWeb page under the first-party HTTPS origin; it stays inside NextN and is not handed to the system browser. The page deliberately has no hard Web trust list because first-party Cloudflare login requires its managed navigation and resources. The application never receives a password or retains browser navigation URLs. A same-origin redirect is not sufficient: cookie capture requires the exact `access_token` marker that the ArkWeb v2 bridge uses to construct `Authorization: User …`; a refresh, legacy, or challenge-only cookie cannot make the native UI claim that the account is signed in. The normalized header and the exact UA configured before that ArkWeb login navigation are sealed together with a device-local non-exportable HUKS AES-GCM key before they enter the private local database; plaintext is held only in memory and is never rendered or logged. A legacy cookie-only record is deliberately rejected at restore rather than guessing an unrelated UA. Authenticated fixed v2 requests do not replay that header through NetworkKit: a root-owned, one-pixel transparent ArkWeb host is lazily bootstrapped at the same HTTPS origin and executes only same-origin GET/POST/DELETE fetches through its own regular cookie/TLS context. Harmony-safe fetch completion is an explicit start, bounded result poll, and immediate page-record cleanup rather than assuming a returned JavaScript Promise is awaited. Its narrowly generated script may read the current `access_token` only inside ArkWeb to construct the required v2 `Authorization: User …` header; the cookie or token never crosses the JavaScript-to-ArkTS result boundary. After promotion only, that same host may fetch the fixed ErosN identity pages and bridge exactly the validated `username`, canonical same-origin `userUrl`, numeric `userId`, and HTTPS `avatarUrl`; HTML, cookies, tokens, headers, and arbitrary page URLs never leave ArkWeb. Those four display fields live in an independent `account_profile` snapshot, restore only after a sealed session restores, refresh best-effort after promotion, and clear on a replacement session, explicit sign-out, invalid restore, or an account GET that enters persisted verification-required state. The host accepts no caller-selected origin, Cookie, User-Agent, or Authorization values and cannot reserve HDS layout space. A cold HUKS key-check, missing-key, decrypt, or envelope failure clears only the in-memory native session/profile presentation, publishes one fixed non-secret restore classification, and retains the sealed ciphertext so a later recoverable platform state can retry it; a non-sensitive account revision is published only for a real signed-in-to-signed-out transition, so an initial no-session restore cannot loop retained Settings. In that retained-record recovery state, Account remains a native verification-required surface; only its explicit Account action registers one replacement-login epoch before any visible Web host may navigate or capture a candidate. That restore path never generates a replacement key. A candidate-login non-2xx is discarded without touching the active record and its exact in-memory candidate is suppressed only until cookie state changes or the visible login attempt restarts, so a challenge page cannot produce a one-second verification loop. A visible-browser candidate is sealed only when the cookie-and-UA snapshot that received a successful account probe remains unchanged immediately after that probe; a changed snapshot stays pending for its own bounded verification. An authenticated idempotent GET that receives `401` may reload the retained host with the sealed UA and issue one replay. Only when that replay is actually issued and also returns `401` does NextN commit a non-secret verification-required marker, then clear runtime/profile state and publish an account revision while retaining the sealed envelope and ArkWeb identity cookies. A failed or blocked recovery leaves the first `401` as a request failure and may not alter durable or published session state. A marker-write failure leaves the prior authenticated runtime unmodified rather than publishing a non-durable recovery state. Cold restore reads that marker before it decrypts or hydrates the envelope, so it neither reuses the token nor automatically opens visible ArkWeb; only the existing explicit Account verification action can do so. A verified visible-login promotion atomically replaces the envelope and clears that marker. A `403` remains a refresh prompt because it can describe a temporary challenge decision. A failed or abandoned candidate also resets the retained host so the next promoted-session request reboots with its sealed UA. Explicit account mutations are never automatically replayed. An explicit confirmed sign-out is the only path that clears the encrypted record; it also expires only the known first-party identity cookies in NextN's regular ArkWeb store, deliberately retaining Cloudflare challenge state. No vote or cross-origin API request is enabled by this boundary.
16. Anonymous Search exposes the ErosN v2 language and order grammar as session-local controls. A language selection is appended to the effective request expression, while non-recent order is sent only as the documented `sort` GET parameter. Its final token autocomplete resolves an explicit namespace from the optional local dictionary first and otherwise makes one anonymous v2 request; an ordinary unquoted final token first uses the local dictionary across namespaces (including bounded translated-label matching for pure CJK), then makes ErosN's bounded tag/parody/character/artist/group probe only when an English-capable input still needs candidates. A selected result replaces only that token with its canonical query. Recent-search history retains the raw submitted text. A control change invalidates earlier pagination and reloads page one using an option snapshot, so a stale page cannot merge into a different query target.
17. Local tag suggestions are optional dictionary-only assistance. A debounced input token must be a final `namespace:prefix` clause (including an unfinished quoted name), then queries only the matching dictionary namespace with an escaped raw-name prefix and a bounded result count. Display names never enter the query. Selecting a candidate replaces only that input token, records local recency after the explicit tap, and still requires the existing Search action before any GET. It never calls a remote suggestion endpoint, learns from typing, scans across namespaces, or reuses the remote-search request generation.
18. The navigation shell, route titles, Back affordance and root tab bar are HDS-owned (`HdsNavigation`, `HdsNavDestination`, `HdsTabs`). Do not reintroduce a page-local header inside that shell or manually reserve the same safe area twice. Root lists reserve only the HDS floating-tab tail; Reader retains its separate immersive chrome.
19. Settings and capability surfaces use concise HDS list rows and grouped sections. A filled action pill, icon tile, or summary card must not be used merely to restate status; Gallery detail and discussion information may use the same grouped-card grammar as NextE where that grouping adds hierarchy.
20. Related galleries are a best-effort anonymous `GET` that begins only after matching detail metadata is verified. It has an independent request generation, retains no error/empty surface, and may render only non-blacklisted compact simple gallery rows. A late, failed, or stale related request must never delay or revoke Gallery metadata, Read, comments, or source-list pagination; selecting a row asks the entry shell to push a new Gallery destination.
21. Page previews are a pushed HDS destination backed only by the already verified detail-page sequence. Its `Grid` uses `GridItem` plus a stable `LazyForEach` data source, loads only preview URLs, and keeps a fixed preview frame so source dimensions cannot destabilise the page grid. Selecting a tile passes its zero-based array index to Reader; a non-negative explicit index is clamped and takes precedence over local resume, while ordinary Read keeps the prior local-resume path. Neither route makes an additional authenticated request or a remote write.
22. Home Browse exposes the same anonymous language/order grammar as Search without generating a user search term. Default All languages + Recent uses the latest page endpoint; every other combination uses a per-generation private negative clause and the documented search `sort` parameter. That clause is neither shown nor written to recent-search history. The active language/order/query snapshot stays fixed for pagination, while any control change starts a new generation. Popular is a separate pushed HDS list backed only by its strict bare-array `GET`; it has no pagination and cannot delay, replace, or poison the main Browse list.
23. Gallery system sharing is an explicit HDS title action backed by Share Kit. It sends only a canonical public HTTPS link derived from the verified numeric gallery id as `HYPERLINK`; it never reads ArkWeb state, adds a title/thumbnail, writes history, configures a target-app allow-list, or exposes cookies/tokens. The adjacent explicit external-open action hands that exact same canonical URL to `UIAbilityContext.openLink()` and no other state. Both actions are outbound only, not a claim that an external HTTPS link can directly reopen NextN: that requires control of the link domain plus a separately configured App Linking contract.
24. Browse and Search follow the NextE HDS entry split: Browse options are a title-bar menu action that opens a native HDS modal sheet; Search input is hosted in the pushed destination's `bottomBuilder`; Search options are a title-bar menu action that opens that same modal shell. Do not return these controls to the scrolling content flow or recreate modal headers in feature pages.
25. Gallery result and related lists use NextE's compact simple-row rhythm: a 72×102 thumbnail, metadata column, transparent host and hairline separator with no inter-row gap. Grouped surfaces are reserved for Gallery header/tags/actions and HDS settings/filter choices; recent searches use small wrapping history chips rather than setting rows.
26. A Gallery header owns the title at rest. After the user scrolls beyond the hero, the route-local Chrome state reveals that same title in the HDS destination bar; Gallery metadata lives in its own compact information group, never as extra hero-card decoration.
27. Reader layout is a local preference with continuous vertical flow plus non-looping paged left-to-right, right-to-left, and top-to-bottom modes. All modes share the same page URL, bounded private cache, zero-based explicit entry index, and serialized local progress record. RTL reverses only the presentation datasource; it retains canonical source indexes for image requests, cache keys, header counts, and persisted progress. Paged modes use a virtualized `Swiper` with one cached neighbour; they must not become an offline/download claim or alter remote requests. A rendered page owns its local two-finger pinch and bounded one-finger pan state. The Reader surface owns double-tap recognition and dispatches a sequence command only to the visible image page, matching NextE's scrolling-recognizer boundary. The child reports only whether it is zoomed: vertical List scrolling and paged Swiper gestures are disabled only while that page is zoomed, with no additional Reader toolbar or global gesture state. Reader chrome starts hidden, is restored by the same exclusive single-tap surface, and overlays rather than reserves the canvas. Its durable Full screen Reader preference hides the status bar only while that chrome is dismissed; the entry-owned Reader destination serializes the official window calls and restores the app status bar before popping the route. The chrome's explicit clock action uses only a bounded durable local interval and begins timing only after the current decoded page is ready; it pauses for a not-yet-ready page, stops at the end, and is cleared on reload or route exit. Volume keys are an explicit false-by-default local preference: while the Reader route is foreground it uses the official InputConsumer only for down→next/up→previous, deliberately consumes the system volume action, and removes both subscriptions on route exit or opt-out so the default system behaviour returns.
28. Reader keep-screen-on is a local preference applied only while the Reader route is visible. The route obtains its own application window, guards asynchronous enables with a session generation, and always requests `false` when it disappears; it must not become an application-wide wake-lock.
29. A user-initiated Gallery download has an isolated durable record, a persisted local worker policy, per-page size limits, and atomic `*.part` promotion inside `context.filesDir`. Its conservative default is one active gallery, three pages per gallery, and two retries; HDS settings expose bounded user choices of one to five gallery workers, one to five page slots, and zero to three retries. A policy change wakes queued work, and a page-slot change applies at the next bounded batch; it never creates a background transfer. A process interruption turns only an in-progress task into Paused; queued work may resume on the next application start. A complete task is eligible for direct Reader entry only when every expected private page still exists. Reader prefers those verified files and otherwise retains its existing read-only network/cache path. This is not an export, archive, background-transfer, or remote-write feature.
30. Content filters are durable local display rules derived from ErosN's block-rule behavior and presented through an HDS Settings destination. NextN supports only gallery title, public-comment author, and public-comment text because the current v2 DTO has no uploader field; ordinary values use case-insensitive containment and regular expressions are explicit. Every affected surface retains the raw successful response and recomputes its visible rows when a rule changes, so enabling, disabling, or removing a rule does not start a new request. Rules live only in the private local RDB, never modify an account, query, or remote resource, and do not suppress a separately opened Gallery detail.
31. The visible ArkWeb account login is a normal browser flow, not a system-browser handoff and not a hidden credential proxy. Before its first navigation it derives the same mobile Android-token UA transform used by NextE, enables regular and third-party cookies, enables DOM storage, and disables the login page cache so a managed challenge can issue fresh browser state. A non-first-party challenge navigation remains `Signing in`, never an `Unavailable` session. Main-frame completion triggers a first-party capture attempt, and while the visible page remains open a serialized timer checks only the trusted login and origin-root cookie scopes; this also covers a same-page login response that has no subsequent navigation. The visible login boundary never runs page JavaScript or reads a form, URL text, cookie value, or browser diagnostic. It merges only syntactically safe cookie pairs in memory and treats a non-empty exact UA plus `access_token` as an in-memory candidate, not a signed-in state. A separate root-owned ArkWeb host then loads the fixed first-party origin with that same UA and issues a status-only request to its fixed account endpoint; the response body never enters ArkTS. Only a 2xx status promotes the candidate into the encrypted versioned session record and publishes an incrementing non-sensitive revision, so retained Favorites and Gallery detail surfaces re-read the verified state rather than keeping stale UI. A 401 clears local identity state; a 403 or transient browser failure remains in the visible sign-in flow and cannot replace a working sealed session. The authenticated transport uses only browser-managed credentials, has a single fixed-origin fetch template, writes a bounded completion record in the document, polls it through synchronous `runJavaScript`, and immediately deletes it before returning only status plus bounded response text. This avoids the documented TLS-fingerprint mismatch of native HTTP clients while preventing a clearance from being replayed under an unrelated app UA. Anonymous requests retain their existing native same-origin GET-only boundary.
32. Settings follows NextE's root-entry hierarchy instead of a flat configuration stack: Account is its own group, while Reader, Download, Cache, Advanced, and About are stable HDS rows that push their own destinations. A root entry may be shown only for an implemented capability. About resolves the installed app version through the native Bundle Manager and remains local; it is not an update checker, browser link, or release service.
33. Candidate-account validation is isolated from active-session expiry: a non-2xx status while the user is still on the visible login Web page drops only the in-memory candidate and continues that page. A terminal `401` from a request made with an already promoted account session enters persisted verification-required state while retaining encrypted identity material and ArkWeb cookies; only explicit sign-out deletes them. This prevents a failed retry or unfinished challenge from silently logging out an otherwise valid session.
34. Only the authenticated Favorites-list read is authoritative for the durable verification-required decision. Profile refresh and Gallery favourite-status enrichment may use the same bounded browser transport, but they are observational: a failed, blocked, or replayed `401` from either one is returned as that request's failure or unknown state and may not publish signed-out state, write the durable verification marker, or alter the sealed envelope. For Favorites, the marker is permitted only after a replay was physically issued and that replay also returned `401`; a first `401` or unavailable replay remains a request failure with the current durable session unchanged.

## Validated anonymous path

The signed client has been exercised on a HarmonyOS device through Browse and Search pagination, Gallery tag-to-search routing, public comments routing and repeatable empty-state reload, Reader progress, reader-image failure/retry recovery, stack Back, cold-start History restore, local recent-search record/reuse/removal, private Reader cache storage/hit after a process restart, and an optional tag-dictionary update/persist/reopen cycle. The dictionary fixture was not exported; the device proof recorded only aggregate local lookup counts and a tag-to-Search route transition. Anonymous Search also exposed all language/order controls and completed an empty benign test query before and after an option reapply; only the fixed-format option summary and empty-state marker were inspected. A later debug-signed 237 run directly compared the root shell with NextE, verified Browse's three direct HDS actions, and followed only native anonymous reads through Popular list content, one Gallery detail, non-empty public Comments, and Reader page `1 / 37`; raw gallery/comment layouts and screenshots were removed after the checks. The local-only suggestion slice, local history removal/clear/search/day-group controls, Reader cache status/clear controls, related-galleries slice, thumbnail-to-explicit-Reader slice, Home's language/order request changes, Gallery Share Kit and external-open actions, and authenticated favourites read await their own signed device run; no runtime claim is made for them yet. Search now has a source-bounded catalog fallback when the optional local dictionary has no exact namespace-prefix candidate, but its network response has not been device-accepted yet. The Account route itself was later reopened through the Settings root on 237 and exposed a visible ArkWeb surface without entering account data; this proves navigation and browser-host creation only, not Cloudflare completion or authentication. The same Settings pass verified root Account/Reader/Download/Cache/Advanced entries and the existing Reader, Download, Cache, and Advanced destinations after the flat root layout was replaced. The local Reader layout menu exposed all four native directions and survived cold starts: LTR advanced from 1/201 to 2/201 on a left swipe, RTL advanced from 1/186 to 2/186 on a right swipe, and top-to-bottom paging advanced from 2/186 to 3/186 on an up swipe. The device was restored to continuous vertical afterward. With the Reader visible and a normal 120-second screen-off timeout, the device remained awake through a 130-second idle window; normal Back returned to Gallery so the Reader lifecycle executed its false reset. The 237 debug-signed download run added an actual 55-page private task, verified its cold-start `Complete` restoration, entered Reader directly through Downloads, and confirmed that Reader selected verified private pages without logging content, paths, URLs, or account state. The following 237 run changed the persisted HDS queue policy from the default 1×3/2-retry setting to 2×2, cold-started the app to confirm the new state, restored the default, and cold-started again to confirm 1×3/2 retries. The later implementation-only 237 installs proved current Debug package replacement and cold launch; they did not perform an authenticated favourite/comment write or type an autocomplete request. This proof applies only to the anonymous read-only and local-private paths; it does not authorize remote-write features.

## Deliberate phase boundary

The native `NhApiClient` makes idempotent NetworkKit `GET` requests for anonymous Browse/Popular/Related paths and browser-context `GET` requests for signed-in favourites reads. It also has three bounded, explicit browser-context account actions: favourite `POST`/`DELETE`, comment `POST` after a fresh bounded SHA-256 proof-of-work, and a torrent-link `POST` that can only issue a short-lived HTTPS capability URL. Comment and favourite writes are reachable only through a visible native HDS action, use one request with no automatic retry, and do not log a body, proof, cookie, token, or response payload. Torrent export additionally requires an explicit confirmation: NextN consumes the validated capability once with a bounded unauthenticated GET into a private temporary `.torrent` file, atomically promotes it after its byte count is verified, and gives only that file URI to the system share sheet. The capability URL is neither persisted, logged, directly opened, nor shared. Browser credentials and the internally derived `Authorization: User …` form are confined to the root-owned fixed `https://nhentai.net/api/v2/` ArkWeb transport; neither reaches image/CDN, torrent-file download, translation, sharing, external-link, arbitrary URL code, or NetworkKit. Local on-device writes are limited to reading history, recent searches, accepted local tag-suggestion recency, app-private Reader cache files, app-private temporary torrent exports initiated by the user, user-initiated app-private download queue files, an explicitly user-triggered optional tag dictionary, and encrypted account-session ciphertext. Authenticated device acceptance for favourites, comments, and torrent export remains pending; no validation task may issue those real remote mutations. Voting, archive download, and background transfer require their own design and device-backed verification before they may be enabled.
